Artifact lands are lands

Zach: "I'm supposed to have 35 lands with the Tony stark deck not 31 but I have
a few artifact lands that are showing up as artifacts instead. Any card with
type land should be a land."

Measured on his deck: Darksteel Citadel, Great Furnace, Seat of the Synod and
Silverbluff Bridge -- all "Artifact Land" -- were filed under Artifact. His
mana base read 31 instead of 35. A deck that looks four lands short is a deck
he would "fix" by cutting spells for lands he already owns.

THE CAUSE WAS ONE ARRAY DOING TWO JOBS. TYPE_ORDER is the Moxfield DISPLAY
order -- Artifact before Land, because that is how the sections read down the
page. sectionFor() then walked the same array to decide which type WINS for a
multi-type card, so Artifact matched first.

Display order and type priority are different questions. TYPE_PRIORITY is now
its own list, starting with Land, then Creature -- an "Artifact Creature" is
still a creature, because that is what you cast and attack with.

deckSections.js already had this right, checking Land first. Only DeckView was
wrong, which is why the backend data was correct all along and the count was
wrong on exactly one screen. Third time on this branch that a second copy of a
rule has drifted from the first.

WHILE FIXING THE TEST FILE I FOUND IT HAD BEEN FAILING SINCE THE DECK-VIEW
REBUILD, and had gone unnoticed because its assertions are bare and top-level:
the first failure aborts the file without naming itself, so the suite reported
one anonymous failure rather than five stale checks.

All five guarded real properties against code that has since moved:

  * every write names BOTH halves of the exact identity (a write missing
    desired_finish lets the server pick, silently turning a foil into a
    nonfoil)
  * an edit is one atomic replace, never delete-then-add
  * every deck capability is still reachable
  * the Collection grid still renders through the shared CardTile
  * cards are sectioned by type

Each is repointed at the file that now owns the behaviour and wrapped in a
test() so a future failure names itself. Two are now checked by BEHAVIOUR
rather than by function name or literal string, so they survive the next
rename instead of breaking and being deleted -- which is how a guard against a
real regression quietly disappears.

Three of my own new guards failed on correct code first: one matched a READ of
desired_card_id rather than a write, one banned DELETE outright when removing a
card legitimately uses it. Fixed the guards, not the app. A test that fails on
correct code is worse than no test -- it trains you to ignore the suite.

DS-TC20 and DS-TC21 verified by reintroducing the bug in both implementations.

343 tests pass, lint and build clean.
