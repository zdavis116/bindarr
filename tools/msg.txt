Show the printing in search results, and fix a raw key on screen

Two things Zach hit on the deployed build.

A RAW KEY RENDERED WHERE A SENTENCE SHOULD BE.

He saw "deck.overCommitted" in the search row. This project's t() resolves a
plural key ONLY when vars.count is a number (translate.js:10). The key is
stored as .one/.other and I called it with { owned, decks } -- no count -- so
the siblings were never consulted and the bare key, which does not exist, fell
through to the screen.

THIRD TIME on this branch, and every time the build and all 343 tests passed.
localeKeys.test.js checked that keys EXIST; nothing checked that a plural key
is called with a count. I18N-TC4 now does, and it immediately paid for itself:
it flagged ExportModal's `t('deck.copyCards', { count })` as missing a count,
which was MY REGEX failing to read ES6 shorthand. A guard with a false positive
is worse than no guard, so that was fixed before the guard was trusted.

Verified by removing the count again and watching TC4 name the exact call.

FOUR IDENTICAL-LOOKING ROWS WERE FOUR DIFFERENT CARDS.

  "we need set numbers in the search results because the 2nd photo is what I
   see so how do I know which to choose?"

Measured -- "Tony Stark" returns four rows reading "Tony Stark / Marvel Super
Heroes", and they are distinct printings:

    #350  Mythic  nonfoil, foil
    #363  Mythic  nonfoil, foil
    #392  Mythic  FOIL ONLY

This app's premise is exact identity: it records the printing owned, not the
card name. A picker that hides the printing asks him to choose blind and then
stores that blind choice as a fact about his cardboard. #392 being foil-only
means one of those rows silently commits to a foil, at a real price
difference -- so foil-only printings are now marked.

Rows show SET #NUMBER, the foil-only marker, then the set name. The commander
picker gets the same treatment, for the same reason.

TESTS: I18N-TC4, DV-TC16 through DV-TC18. 343 pass, 0 fail. Lint and build
clean.
