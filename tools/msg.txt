Both from Zach on the deployed build.

IMPORT LOST MOST OF A MOXFIELD DECK.

"I imported a full deck from moxfield and only a few cards filled the deck."
Reproduced exactly: 25 copies requested, 13 written, 12 silently gone.

Not a parser bug. "1 Lightning Bolt" with no set code names a card with 65
printings, and this app records the EXACT printing you own. When none is owned
there is nothing to infer from, so the server deliberately writes nothing and
returns needs_choice with the printings to offer (routes/decks.js:1645). That
design is right -- guessing would put a printing he does not own into his deck.

The bug was mine: I called apply:true straight from the new-deck modal, so
every line awaiting a choice was discarded. The cards that DID land were the
ones already in his collection, which is exactly why "only a few filled the
deck" and why it looked arbitrary.

Now the modal previews first. Nothing ambiguous -> apply immediately, the
common case for an owned or set-qualified list. Anything ambiguous -> the deck
is created with the unambiguous cards and the existing printing picker opens
with the rest, which are one screen away rather than lost.

Verified end to end: preview offered 92 printings for Lightning Bolt, 171 for
Sol Ring, 1102 for Island; answering them gave requested=12 written=12
unresolved=0.

I also passed the whole response where the modal reads the LINES array, which
would have rendered an empty picker -- caught by lint, not by the build.

LONG-PRESS TO DELETE DOES NOT EXIST ON A PHONE.

"I still can't delete decks. Long pressing a row doesn't do anything."

onContextMenu fires on a desktop right-click; on mobile Safari a long-press
raises the system selection menu instead. So the only route to delete was a
gesture unavailable on the only device this app is used on. Replaced with a
Delete action in the selection mode that already exists for the buylist --
deliberately not a per-row button, which is a mis-tap that destroys a deck.

AND THE FIX FOR IT WAS ITSELF UNREACHABLE. The delete button added to the deck
view is the last element on a scrolling screen, and DeckView had no
paddingBottom -- so on any real deck the pinned nav bar covered it. Twelfth
control on this project hidden by that nav; now cleared like DeckList does.

343 tests pass, lint and build clean.
