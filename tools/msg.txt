Owned means usable here; share the export dialog with the deck list

Both bugs are Zach's, from using the deployed build, and both are the same
mistake in different clothes: treating "he owns a copy" as "a copy is free for
this deck".

OWNED AND MISSING SHOWED THE SAME CARD.

  "if I add Tony stark to that deck he shows in both owned and missing but for
   that deck he would be missing because his other copy is used in another
   deck."

He owns one Tony Stark and another deck has it, so for the deck on screen:

    quantity_owned     = 1   he has one, somewhere
    quantity_available = 0   none free -- the other deck holds it
    quantity_missing   = 1   he must buy one to finish this deck

The Owned tab tested quantity_owned, so the card satisfied Owned AND had a
shortfall, landing in both. The progress ring counted it too, so the deck read
as more finished than it is -- it would say ready while the card sits in a box
across the room. That is a wrong record, not a cosmetic slip: the failure Zach
minds most, because he only discovers it standing at the binder.

Owned is now "nothing missing", which makes the two tabs complementary by
construction rather than by two filters agreeing. Progress counts
quantity_available for the same reason. The server already computed all three
figures correctly (deckIdentity.js:198-230) -- the client was reading the wrong
one.

"1 IN THIS DECK" WAS ABOUT A DIFFERENT DECK.

  "when I do Tony stark it says 1 in this deck which it's not in the deck I'm
   searching but it is in a different deck"

in_deck_qty from /api/search counts copies committed ACROSS ALL DECKS, and
deliberately so -- availability is a whole-collection fact (routes/collection.js
:46). Labelling it "in this deck" inverted its meaning: it announced the card
was already here, when being elsewhere is precisely why it shows as missing.

The count for THIS deck comes from the deck the component already holds, so
both facts are now shown and worded apart: "1 already in this deck" versus
"1 owned, in other decks".

ONE EXPORT DIALOG, SHARED.

  "for the deck list when selecting multiple decks for the buylist can we have
   the functionality be the same as for the missing in the deck view."

They had drifted: the deck view opened a modal with three formats and showed
the text before copying; the deck list silently put one fixed format on the
clipboard, so you could not see what you were about to paste. ExportModal.jsx
is now used by both -- shared rather than copied, because two copies of an
export dialog is how they diverged in the first place.

TESTS: DV-TC9 through DV-TC12. The first three were verified by REINTRODUCING
each bug and watching the case fail -- Owned tested by ownership, progress
counting owned-anywhere, and the all-decks figure relabelled as this deck.

343 pass, 0 fail. Lint and build clean.
