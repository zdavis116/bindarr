**Written:** 2026-08-30
**Owner:** Zach (YoungsterZach)

Ordering is Zach's, confirmed 2026-08-30:

> "current scanning feature branch then the UI overhaul using those mocks and
> then this importer and scryfall sync being the 3rd feature"

Each feature is its own branch. Nothing goes to production; `main` merges need
review plus all checks passing.

---

## Standing constraints (apply to all three)

- **A wrong record is far worse than a missing one.** A missing card costs one
  tap; a wrong card costs a physical recount against cardboard.
- **No silent state changes.** If the app changes what Zach owns, he must be
  able to see it happened.
- **Verify a test fails with the bug reintroduced** before counting it as
  coverage. This has caught four worthless tests this week.
- **Verify the served bundle**, not just the commit, before saying "ready to
  test". Always include the dev URL.
- **No redundant surfaces.** Zach has rejected: a separate review queue, a
  separate buylist panel, advisory flags, and a `Missing` filter inside
  Collection.
- Dev deploys need `export PATH=/opt/node20/bin:$PATH`.

### Locked design decisions

- **Dark theme, complete overhaul.** Existing navy/red identity is replaced.
  Tokens: `--bg:#000`, `--surface:#1c1c1e`, `--surface-2:#2c2c2e`,
  `--surface-3:#3a3a3c`, `--ink:#f5f5f7`, `--ink-2:#98989d`, `--ink-3:#636366`,
  `--accent:#0a84ff`, `--have:#30d158`, `--need:#ff9f0a`.
- **Three nav destinations: Home, Collection, Decks.** Scan is NOT a tab — the
  Home hero button replaces it.
- **Home stays the landing screen.** Leads with a full-width "Scan cards"
  action, then decks-in-progress with completion rings and cost-to-finish,
  then collection stats last and small.
- **Collection shows only owned cards.** No missing/needed concept — Zach:
  "it muddies the water."
- **Collection filters:** five WUBRG pips, **multi-select** (a Golgari card is
  B *and* G — single-select cannot express it). Types and Sets are
  **multi-select sheets**, because a card can be Creature *and* Enchantment.
  Bottom sheet on mobile, centred dialog on desktop.
- **Deck: Missing IS the buylist.** No separate panel. The Missing tab carries
  the running total and the Export button.
- **Multi-deck buylist buys ONE COPY PER DECK — not deduped.** Zach: "if I
  select 3 decks and even one needs a sol ring there should be 3 sol rings in
  that list not 1... I'd rather each deck be built ready to go."
- **New deck: format first, ten formats.** Commander and Bracket sections only
  exist for formats that have them; hidden, not disabled. Switching away from a
  commander format clears the chosen commander.
- **Desktop:** Home and Collection reflow (rail replaces tab bar). Only the
  **deck builder** gets a distinct two-pane layout — deck left, owned cards
  right, add/remove on hover.
- **44px minimum touch targets** everywhere; `env(safe-area-inset-*)` respected.
- **Four nav destinations, not three.** Settings joins Home / Collection /
  Decks. Scan is still NOT a tab.
- **Sync is ONE section in Settings**, not scattered buttons. Every source
  answers the same three questions: connected?, last run?, what changed? A sync
  that fails silently is the same failure class as a scanner that stops
  silently — indistinguishable from working.
- **Sync sources:** card catalogue (Scryfall, nightly, already built) and
  Moxfield decks (Feature 3+). Status is a word plus a dot, never colour alone.
- **Moxfield is pull-only for now.** Two-way sync needs a rule for which side
  wins when both changed, and a wrong deck is harder to notice than a missing
  one. The screen states this plainly rather than leaving it implied.
- **Admin is reached from Settings → About → Administration**, not a nav tab.
  It mirrors what `AdminPanel.jsx` already does: users/roles, instance base
  URL, catalogue refresh, test data. **Scan indexes are removed** — see Phase C
  task 13; zero have ever been built on either host.
- **One "Data sources" section, not Sync + Connected accounts.** Zach: "sync
  and connected accounts separate is confusing." The split was arbitrary — it
  divided sources by whether they need a login, which is an implementation
  detail. He cares which sources are current and which are stale, not which
  hold credentials. One row per source, each stating what it is, when it last
  ran, and whether that is OK; tapping opens its detail. A new source
  (TCGplayer, Archidekt) is then one more row, not another section.
- **Each source reports what its last sync CHANGED**, not just that it
  succeeded ("Added 238 cards · Tarkir: Dragonstorm"). "Completed" is not
  checkable; a delta is.
- **Destructive admin actions are physically separated**, in a bordered danger
  zone — not one row below a routine action where a mis-tap reaches them.
- **Long admin jobs report progress.** A job that churns silently for minutes
  is indistinguishable from a hang.

# Feature 3 — ManaBox import + Scryfall sync (`feat/collection-import`)

**Goal:** import Zach's ManaBox collection, and keep the catalogue current.

## What the real data says

Measured against `ManaBox_Collection.csv` (2026-08-30) and the live dev
catalogue (105,462 rows):

```
1,295 rows   (2,319 cards once Quantity is summed)

matched by Scryfall ID   1,276   98.5%
not in catalogue            19    1.5%   ← all tokens (TTLA, TMSH, TTMT)
```

**Every row carries a Scryfall ID.** This is the finding that shapes the whole
feature: ManaBox exports the exact printing UUID, so matching is a primary-key
lookup, not a parse of set code + collector number. No ambiguity, no
leading-zero or rarity-letter handling, none of the failure modes the scanner
fights.

Other facts from the file: every row is `Language=en`, `Condition=near_mint`,
`Misprint=false`, `Altered=false`. 10 foils out of 1,295. 61 distinct sets.

**Tokens are excluded by decision.** Zach: "tokens can be ignored I will remove
them from ManaBox before doing the sync... I don't want tokens in my
collection." The importer should still REPORT any unmatched row rather than
drop it silently.

## The Scryfall sync mostly already exists

`backend/src/cardCatalogue.js` already downloads Scryfall's `default_cards`
bulk file and refreshes `card_cache`. `server.js:205` runs it **nightly**
in-process, guarded by the Scryfall build timestamp so it will not re-download
the same build. `CARD_CATALOGUE_REFRESH=off` disables it.

The dev catalogue was refreshed **2026-08-30 12:57** — it is not stale.

So Feature 3 does NOT need a sync built from scratch. What it needs:
1. Confirm the nightly refresh is actually running on both hosts (check
   `last_updated` drift over several days — do not assume).
2. Surface catalogue freshness in the UI, so "card not found" is diagnosable.
3. A manual "refresh catalogue" trigger for after a set release.

## Why import is currently disabled

`backend/src/routes/importExport.js` returns **501** on purpose:

> "Import is intentionally disabled until the Oracle-aware importer can validate
> every row against an English Scryfall printing. Trusting uploaded metadata
> here would bypass the card-admission boundary and poison the shared cache."

That boundary is correct and must survive: `card_cache` is the shared catalogue
everything trusts (prices, legality, deck buylists). A row written from
uploaded text becomes a permanent fake card indistinguishable from a real one.

**The design rule:** import may only ADD `collection` rows pointing at
`card_cache` entries that already exist. It must never INSERT into `card_cache`.

## Task sequence

**Phase A — parsing and matching (no writes)**
1. Extend `backend/src/utils/csvMappers.js`: add `Scryfall ID` as the primary
   key for the ManaBox strategy, with set+number as fallback.
2. Test: parse Zach's real CSV, assert 1,295 rows and that every row yields a
   Scryfall ID. Fixture: a trimmed copy of the real file.
3. New `backend/src/utils/importMatcher.js` — takes parsed rows, returns
   `{ matched, unmatched }` by `card_cache.id` lookup. **Never writes.**
4. Test: matcher rejects a row whose ID is absent, and NEVER invents a card.
   Verify it fails if the guard is removed.

**Phase B — the endpoint**
5. Replace the 501 in `importExport.js` with a two-step flow:
   `POST /api/import/preview` → counts + unmatched list, writes nothing.
   `POST /api/import/commit`  → adds matched rows to `collection` only.
6. Both scoped by `user_id`. Commit runs in ONE transaction so a failure at row
   900 does not leave a half-imported collection.
7. Test: a preview writes nothing; a failed commit leaves the collection
   unchanged. Verify by breaking the transaction deliberately.
8. Cap upload size and row count; reject a file that is not a CSV.

**Phase C — UI (mockup `006-import`)**
9. Entry point: the `+` menu in Collection (Scan / Import / Search).
10. Source picker → progress → review → done.
11. Review screen shows both counts, lists unmatched rows WITH the reason, and
    states plainly that unmatched rows are skipped, never guessed.
12. 2,319 cards is small enough to import in one request; no batching needed.
    Show progress anyway — a silent 10-second wait reads as a hang.

**Phase D — catalogue freshness**
13. Expose `last_updated` max from `card_cache` in Settings.
14. Manual "Refresh catalogue now" button calling the existing
    `refreshCatalogue()`.
15. Verify the nightly job has actually run on prod and dev by checking
    `last_updated` on consecutive days. Do not assume from reading the code.

### Decided (Zach, 2026-08-30)

- **Re-import is allowed, behind a confirmation modal, and it ADDS quantities.**
  Zach: "We should allow re-import only with confirmation modal and it will
  double the quantities."

  Rationale: the importer cannot tell "I re-imported the same file by mistake"
  from "I bought a second copy of everything and re-exported." Only Zach knows
  which, so the app must ask rather than guess. Silently overwriting would lose
  a genuine second copy; silently adding would double a collection on a
  double-tap. The modal is what makes the state change non-silent, which is the
  standing rule.

  The modal must state the consequence in counts, not adjectives:
  "Add 2,319 cards to your collection? Cards you already own will go up, not be
  replaced. Sol Ring 4 → 5." Cancel is the default action.

  Implementation: `POST /api/import/commit` takes an explicit
  `confirm_duplicates: true` when any incoming row matches a card the user
  already owns. Without it the endpoint returns 409 with the overlap count, so
  a client that forgets the modal cannot double a collection by accident.

- **Purchase price is ignored for now.** The column is parsed and discarded, not
  written. Revisit only if Zach asks for cost-basis reporting.

### Risks
- **Poisoning the catalogue** is the one unacceptable outcome. The importer must
  be structurally incapable of writing to `card_cache` — enforce with a test
  that fails if an INSERT into `card_cache` appears in the import path.
- A partial import is a silent wrong state. One transaction, or nothing.
- **Doubling a collection without being asked** is the "wrong record" failure
  Zach cares most about. The 409-without-confirmation guard exists so this
  cannot happen through a client bug, not only through UI discipline.
- Foil handling: 10 rows are `Foil=foil` → must map to `finish='foil'`, and
  `finishColumnsFromBody` is the single place that interprets a finish.
